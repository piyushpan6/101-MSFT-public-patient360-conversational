3. Target design

  • Toggle: each tab selects its backend. A server env flag P360_BACKENDS=ghcp,foundry can turn Foundry off, which hides its tab, so the demo can always fall back.
  • Reused unchanged: tools.py schemas, rules.py instructions, page tools, cards, figure numbering, trace, and chat history (records gain a backend field).
  • New code (Foundry adapter): streams Responses events into delta / reasoning / tool / tool_done / done, runs the tool loop with page_call(), keeps the conversation with previous_response_id, and supports stop/abort.
  • Data access: the page still reads OneLake through the existing functions. Foundry never touches patient data directly, the same as GHCP today.

5. Regression plan (GHCP path must not break)

Before touching code
  1. Get the app running locally (npm run dev:local plus chat/server.py) on Windows.
  2. Run the existing chat/dev/eval.py on a smoke subset (--only st-,c-,p-) and save it as the GHCP baseline.
After every step
  1. New fast tests: event-contract tests (both backends emit valid NDJSON), and a check that GHCP request handling is unchanged when backend is missing.
  2. Re-run the GHCP smoke eval and compare it with the baseline. Any new flag blocks the commit.
  3. eval.py --backend foundry runs the same cases on the new tab for a side-by-side score.
